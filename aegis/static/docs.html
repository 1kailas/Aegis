Overview & Architecture

Aegis AI is an autonomous infrastructure engineering control plane that continuously monitors host health, orchestrates Docker and Kubernetes workloads, profiles AI hardware, and delegates repairs to Devin.

The Central Architectural Principle

Core Safety Invariant
Aegis monitors and orchestrates. Deterministic controllers enforce safety. AI investigates and engineers fixes. Independent verification determines whether the fix actually worked.

Traditional monitoring tools alert on-call SREs after a system has failed. Runaway LLM agents, by contrast, risk catastrophic host damage when given unconstrained shell access. Aegis bridges this divide with a dual-plane architecture that physically decouples autonomous diagnosis from deterministic safety enforcement.

Dual-Plane Safety Architecture & The Three Operational Planes

1. Deterministic Safety Plane

Operates 100% locally and deterministically. Evaluates Linux Pressure Stall Information (PSI), CPU thermal throttling states, memory exhaustion, and NVMe health. Critical thresholds, hysteresis curves, and cooldown periods are hardcoded and mathematically bounded. No AI model has permission to alter physical safety boundaries.

2. AI Diagnostic & Engineering Plane

When an incident occurs, telemetry, metrics, and redacted logs are analyzed by a hierarchical 3-tier diagnosis engine (Local Ollama → Cloud Gemini → Deterministic Expert Heuristics). If the incident stems from a code or configuration defect, Aegis drafts a structured RepairTask specification and delegates it to Devin as its designated software repair engineer.

3. Independent Verification Plane

Aegis never trusts patches blindly. Proposed fixes are validated inside ephemeral git clones (repair-workspaces/<task_id>) with strict patch scope enforcement (rejecting modifications to .env files or parent directory traversal). Once merged, Aegis executes independent live health probes before marking the incident resolved.

5-Minute Quickstart

Deploy the Aegis AI control plane server and inspect local infrastructure in under five minutes.

1. Start the Aegis Server

Select your deployment method below to run the server:

# 1. Clone the repository
$ git clone https://github.com/1kailas/Aegis.git
$ cd Aegis

# 2. Create Python virtual environment
$ python3 -m venv .venv
$ source .venv/bin/activate
$ pip install -e .

# 3. Start the Aegis Server
$ aegis-server --host 0.0.0.0 --port 8000
# Deploy Aegis Server and Agent via Docker Compose
$ git clone https://github.com/1kailas/Aegis.git && cd Aegis
$ docker-compose up -d
# Automated Linux service installer
$ curl -sSL https://raw.githubusercontent.com/1kailas/Aegis/main/scripts/install.sh | bash -s --role server

2. Verify Running Endpoints

Once started, test that the API is responding to health probes:

$ curl -s http://127.0.0.1:8000/api/health | jq .
{
  "status": "ok",
  "version": "3.2.0",
  "engine_running": true,
  "mode": "monitoring_only",
  "emergency_stop": false
}
import urllib.request, json

resp = urllib.request.urlopen("http://127.0.0.1:8000/api/health")
health = json.loads(resp.read())
print(f"Aegis status: {health['status']} (v{health['version']})")

3. Explore the Unified SRE Dashboard

Open http://localhost:8000 in any browser to inspect:

  • Real-time Telemetry: CPU utilization sparklines, RAM pressure, and PSI stalls.
  • Cluster Mesh: View registered worker nodes, statuses, and fleet capacities.
  • Model Hub & Deployer: Inspect recommended AI models and deploy inference engines in one click.

Distributed Cluster Mesh & Remote Node Joining

Connect any Linux client machine to the Aegis server using only the server IP address.

Zero-Dependency Remote Joining

To eliminate developer friction, the Aegis telemetry agent is self-contained. It uses the Python standard library (urllib.request, /proc/meminfo, os.getloadavg) when third-party libraries like psutil or httpx are absent.

# Stream and execute standalone agent.py directly on the worker device
$ curl -sSL http://<SERVER_IP>:8000/agent.py | python3 - <SERVER_IP>
# Install and enable as a systemd background service
$ curl -sSL http://<SERVER_IP>:8000/install.sh | bash -s <SERVER_IP>
# Join via the unified aegis CLI tool
$ aegis join <SERVER_IP> --labels role=worker,zone=us-east-1

Managing Cluster Nodes

Operators can inspect and drain nodes before scheduled maintenance:

$ aegis nodes list
---------------------------------------------------------------------------------
NODE ID             HOSTNAME         IP ADDRESS       STATUS   CPU%   RAM%   VRAM
---------------------------------------------------------------------------------

worker-node-2       gpu-node-2       10.0.1.26        ONLINE   12.4%  18.5%  16.0 GB
---------------------------------------------------------------------------------
# Cordon and drain node to prevent workload assignment
$ aegis nodes drain worker-node-1

Docs / AI Model Hub / Hardware Profiling & Tiers

Hardware-Aware AI Model Intelligence

Inspect host GPU VRAM, system RAM, and CPU core counts to evaluate model feasibility and avoid out-of-memory crashes.

Deterministic Fit Tiers

Aegis compares open-source weights against available hardware, categorizing models into four deterministic fit tiers:

Tier Hardware Requirement Inference Behavior
OPTIMAL Weights and 32k KV cache fit 100% inside physical GPU VRAM. Peak tokens/sec throughput, zero CPU swap, instantaneous Time-To-First-Token (TTFT).
GOOD Weights fit in VRAM with headroom for standard 4k-8k context. High throughput with minimal latency penalty.
MARGINAL Exceeds VRAM; requires layer spilling across the PCIe bus into system RAM. Significant throughput drop (4x–10x latency penalty) due to memory bus bottlenecks.
INCOMPATIBLE Exceeds combined VRAM and system RAM capacity. High risk of CUDA Out-Of-Memory (OOM) process kill or system unresponsiveness.

Running Model Assessment via CLI

$ aegis models recommend
$ aegis models recommend --task CODING

Docs / AI Model Hub / 1-Click Docker & K8s

One-Click Cloud Native Deployer

Provision AI model inference containers to Docker or Kubernetes with automated GPU passthrough and readiness probes.

Deploying to Docker

Aegis launches a container with GPU device passthrough (--gpus all) and persistent model cache:

$ aegis models deploy qwen2.5-coder:7b --runtime docker --port 11434
$ curl -X POST http://127.0.0.1:8000/api/models/deploy \
  -H "Content-Type: application/json" \
  -d '{"model_name": "qwen2.5-coder:7b", "runtime": "docker", "port": 11434, "gpu": true}'

Deploying to Kubernetes

Aegis generates production-ready YAML manifests including resource requests and limits (nvidia.com/gpu: 1) and healthcheck probes:

$ aegis models deploy deepseek-r1:8b --runtime k8s --port 11434
$ curl -s "http://127.0.0.1:8000/api/orchestration/manifests/k8s?model_name=deepseek-r1:8b" | jq -r .manifest_yaml

Real-Time Model Benchmarking

Empirically measure inference performance down to the millisecond with live streaming probes or physical bandwidth simulation.

Metrics Evaluated

  • Time-To-First-Token (TTFT): Latency from dispatch until the first token is emitted (ms).
  • Decoding Throughput: Sustained token generation speed (tokens/second).
  • Prompt Evaluation Speed: Time to process the input prompt context (tokens/second).
$ aegis models benchmark qwen2.5-coder:7b
✔ Benchmark Completed (COMPLETED):
  Model:             qwen2.5-coder:7b
  Throughput:        38.4 tokens/sec
  Time-To-First-Tok: 142.5 ms
  Prompt Eval Speed: 185.0 tokens/sec
  Tokens Generated:  60
$ curl -X POST http://127.0.0.1:8000/api/models/benchmark \
  -H "Content-Type: application/json" \
  -d '{"model_name": "qwen2.5-coder:7b"}' | jq .

Dynamic VRAM Optimizer & Eviction

Reclaim GPU VRAM and host RAM by proactively unloading idle model instances during resource pressure.

When system memory or thermal alerts trigger, the memory optimizer scans active model-serving runtimes and unloads idle models using keep_alive: 0:

$ aegis models optimize
✔ Memory Optimization Complete:
  Unloaded Models: deepseek-r1:14b
  Reclaimed VRAM:  10440.0 MB
$ curl -X POST http://127.0.0.1:8000/api/models/optimize | jq .

Closed-Loop Self-Healing Lifecycle

Aegis connects anomaly detection, AI diagnosis, policy authorization, and live recovery verification into a closed-loop incident lifecycle.

Lifecycle States

State Phase Description
DETECTED Detection Guardian or container probe identifies threshold breach or crash loop.
INVESTIGATING Diagnosis 3-tier diagnosis engine synthesizes root cause hypothesis.
CONTAINED Remediation Allowlisted operational remediation executed in policy_autonomous mode.
REPAIRING Engineering Non-trivial code/config bug delegated to Devin repair task.
RECOVERY_VERIFIED Resolution Independent live probes confirm workload stabilized within nominal tolerances.

Devin Autonomous Repair Protocol

Delegation of complex code and configuration bugs to Devin with isolated git sandboxes and evidence-backed PRs.

Security Sandboxing

Aegis clones the repository into an isolated directory (repair-workspaces/<task_id>) and verifies that patches:

  • Never modify .env files or secret configurations.
  • Never alter CI/CD GitHub Actions workflow definitions.
  • Never attempt directory traversal (../).

SRE Operations & Troubleshooting FAQ

Frequently asked architectural questions, production deployment recipes, and debugging procedures.

Frequently Asked Questions

Q: Does Aegis require an NVIDIA GPU?

No. When an NVIDIA GPU is not detected, Aegis gracefully marks GPU sensors as UNAVAILABLE. The Model Recommender automatically adapts, recommending CPU-compatible quantized models without fabricating telemetry.

Q: Can Aegis operate completely offline?

Yes. Host telemetry collection, deterministic thermal and resource guardians, local Docker orchestration, offline rule-based diagnosis, and local model serving run 100% offline.
